# Фаза 1 — конвейер захвата. План работ по PR

Цель фазы: доказать главную гипотезу проекта — **из захваченного трафика механически
получается работающая декларация**. Проверка на DeepSeek, для которого правильный ответ
уже известен (`server.js:529-676` + `docs/api-documentation.md`).

Порядок изменён относительно §8.2: CDP-рекордер идёт раньше расширения (риск R-1 —
MV3 не отдаёт тела ответов, расширению нужен `chrome.debugger`, это отдельная и более
дорогая работа).

---

## PR-0. Скелет монорепо и CI *(формально фаза 0, но фаза 1 без него не собирается)*

- pnpm workspaces + Turborepo, базовый `tsconfig` (strict, ESM, `NodeNext`), tsup, vitest.
- `packages/schema` с пустыми экспортами, `packages/capture`, `packages/testkit`.
- Текущий проект целиком переезжает в `legacy/` **без изменений** и продолжает
  запускаться командой `pnpm legacy:start`.
- CI: lint + typecheck + `vitest run` + запуск старых тестов `legacy/tests/unit.test.js`.

**Критерии приёмки:** `pnpm i && pnpm build && pnpm test` зелёные на чистой машине;
`pnpm legacy:start` поднимает текущий сервер и отвечает на `/health`; старые 735 строк
тестов проходят без правок.

## PR-1. Модель захвата и HAR-импорт

`packages/capture`:
- Zod-схема `CaptureBundle` / `CaptureEntry` (см. `03-interfaces.ts`) в `packages/schema`.
- Импорт HAR 1.2: разбор `log.entries`, восстановление `headerOrder` из исходного
  порядка, декодирование `content.text` с `base64`.
- Восстановление SSE: HAR хранит тело потока одной строкой — разбиваем на кадры по
  `\n\n`, сохраняем в `frames` (тайминги при импорте из HAR отсутствуют, помечаем `at: null`).
- CLI: `omniproxy capture import <file.har> --provider <id> --scenario <name>`.

**Критерии приёмки:** импорт HAR, сохранённого из DevTools на любом SSE-сайте,
даёт бандл, в котором количество entries совпадает с числом запросов в HAR,
а SSE-ответ разложен на кадры; юнит-тесты на фикстуре HAR в репозитории.

## PR-2. Санитайзер (блокирующее требование §8.4)

- Детекторы секретов: значения известных cookie-имён из декларации, `authorization`,
  `set-cookie`, JWT по форме, длинные hex/base64-значения (> 24 симв. и высокая
  энтропия), e-mail, телефоны, `user_id`-подобные поля.
- Замена на стабильные плейсхолдеры (`{{redacted:token:1}}`), запись соответствия
  **вида** секрета в `redactions` — без значений.
- Санитизация обязательна и неотключаема: `CaptureBundle.sanitized !== true` →
  запись на диск в `fixtures/` отклоняется.
- Отдельный «сырой» кэш живёт только в памяти процесса и в `.omniproxy/tmp` с
  правами 600 и TTL 1 час, в git не попадает (`.gitignore` + проверка в CI).

**Критерии приёмки:** тест «загрузить бандл с живыми cookie/JWT → в сохранённом файле
ни одного исходного значения»; grep-тест в CI, который валит сборку при обнаружении
похожего на секрет значения в `packages/providers/*/fixtures/**`.

## PR-3. Анализатор захвата

- Фильтрация шума: аналитика (белый список доменов + эвристики `/log`, `/track`,
  `/beacon`, `sentry`, `ga`), статика по mime и расширению, preflight `OPTIONS`.
- Классификация оставшихся вызовов в `CaptureEntry.classification` по признакам:
  наличие `set-cookie` → auth; ответ с идентификатором, который потом появляется в URL
  следующего запроса → session; `text/event-stream` → stream; повторяющийся GET с
  монотонно меняющимся телом → poll; `PUT` на другой хост с бинарным телом → upload;
  ответ с `video/*`, `image/*`, `audio/*` → artifact.
- Восстановление последовательности: граф зависимостей по «значение из ответа A
  встречается в запросе B».
- Diff между двумя бандлами одного сценария → заполнение `volatileFields`
  (это ровно те поля, которые в декларации станут `{{...}}`).

**Критерии приёмки:** на двух захватах DeepSeek анализатор находит цепочку
`create_pow_challenge → chat_session/create → chat/completion`, помечает
`chat_session_id` / `parent_message_id` / PoW-заголовок как volatile, а телеметрию
отбрасывает; результат проверяется юнит-тестом против ожидаемой цепочки.

## PR-4. Минимальный движок деклараций

`packages/engine-declarative` — ровно столько, чтобы сгенерированный черновик можно было
исполнить и проверить:
- шаблонизатор `{{...}}` с закрытым списком модификаторов;
- подмножество JSONPath для `extract` и `stream.map`;
- исполнитель `flow` для `createSession` / `send`, `HttpClient` через порт;
- парсеры framing: `sse`, `ndjson`, `json-patch` (нужен для DeepSeek);
- реестр transforms с первыми элементами: `uuid-v4`, `base64`, `json-stringify`,
  `hmac-sha256`, `deepseek-pow-v0` (обёртка над портированным `lib/pow.js`).

**Критерии приёмки:** движок исполняет вручную написанную декларацию DeepSeek против
replay-фикстуры и отдаёт тот же текст ответа, что и `legacy/server.js` на том же входе
(golden-тест, сравнение посимвольно, включая порядок reasoning/text-дельт).

## PR-5. Генератор черновика `provider.yaml`

- Из проанализированного бандла: `channels[0]` (base, статические заголовки, headerOrder,
  профиль отпечатка по User-Agent), `auth.harvest` (по именам cookie из `set-cookie`
  и заголовка `cookie`), `flow.createSession` / `flow.send` / `flow.poll`,
  `stream.format` + черновой `map` (по путям, где в кадрах меняется строковое значение),
  `errors` (по не-2xx ответам в бандле).
- Всё неразрешённое — в `notes` и в YAML-комментарии `# TODO(capture): ...`:
  необъяснимые заголовки, значения без источника в предыдущих ответах, PoW/подписи.
- Черновик всегда получает `status: needs-capture` и `class: unknown` — человек обязан
  проставить их руками.

**Критерии приёмки:** `omniproxy capture analyze` на бандле DeepSeek выдаёт YAML,
который после **не более чем 10 строк ручных правок** проходит `provider validate`
и golden-тест из PR-4. Число правок фиксируется в отчёте фазы — это и есть измерение
качества конвейера.

## PR-6. Replay-харнесс и контрактные тесты

`packages/testkit`:
- `ReplayHttpClient`: сопоставляет исходящий запрос с записью бандла (метод + путь +
  нормализованное тело), отдаёт записанный ответ и кадры с исходными таймингами.
- Несовпадение запроса — не «промах кэша», а падение теста с diff'ом (иначе тесты
  начинают лгать, риск R-7).
- Диффер схем: фактический JSON против записанного — список путей
  «появился / исчез / сменил тип», в человекочитаемом виде.
- `defineContractTest(providerId)` — один вызов на провайдера.

**Критерии приёмки:** контрактный тест DeepSeek проходит офлайн, без сети и без
аккаунта; искусственное изменение пути в фикстуре даёт понятный diff, а не стектрейс.

## PR-7. CDP-рекордер

`omniproxy capture record <provider>`:
- обобщение `scripts/deepseek_chrome_auth.js` (там уже есть запуск Chrome, CDP по
  WebSocket, `Runtime.evaluate`, `Network.getAllCookies`) — выносим в `packages/auth`
  общий CDP-клиент;
- подписка на `Network.requestWillBeSent` / `responseReceived` / `loadingFinished` /
  `getResponseBody` и, отдельно, `Network.eventSourceMessageReceived` для SSE
  (единственный способ получить кадры с таймингами);
- интерактивный сценарий: «войдите → выполните действие → Enter», на выходе — бандл,
  прогнанный через санитайзер;
- одновременно снимается credential (та же сессия) — авторизация и захват одним проходом.

**Критерии приёмки:** запись сценария на живом DeepSeek даёт бандл, из которого PR-5
генерирует черновик, проходящий golden-тест. **Этот критерий требует живого аккаунта
пользователя** (риск R-11) — до его выполнения фаза 1 считается незакрытой.

## Что фаза 1 НЕ делает

Ни ядра, ни роутера, ни протоколов, ни job-модели, ни новых провайдеров. Движок
деклараций пишется в объёме «достаточно для DeepSeek» и будет дополняться в фазе 2.
Старый `server.js` всё это время остаётся единственным рабочим сервером.

## Метрика успеха фазы

**Число ручных правок в сгенерированном черновике до прохождения golden-теста.**
≤ 10 строк — конвейер работает, идём в фазу 2. 30+ строк — гипотеза проекта не
подтвердилась, надо либо радикально усиливать анализатор, либо признать, что
адаптеры пишутся руками, и пересобирать план вокруг этого.

---

## Поправка после ADR-0003

Конвейер захвата с самого начала пишется как **пользовательский** инструмент, а не как
внутренний скрипт:

- `omniproxy capture record|import|analyze` принимают произвольный `<id>`, в том числе
  провайдера, которого нет в репозитории; результат кладётся в `~/.omniproxy/providers/<id>/`.
- Санитайзер (PR-2) и ограничение хостов (`allowedHosts`) — не «best practice», а условие
  того, что декларациями можно безопасно обмениваться.
- Диагностика в `provider try` пишется на языке автора модуля («JSONPath не нашёл поле,
  в ответе есть такое-то»), а не в терминах внутренних компонентов.

Загрузчик внешних модулей и граница доверия въезжают в фазу 2 вместе с реестром —
дописывать это после означает переделывать реестр.

### PR-1 — выполнен (2026-08-27)
`packages/capture` + `apps/cli`.

Сделано:
- `CaptureBundle` / `CaptureEntry` / `CaptureFrame` в `packages/schema` (zod).
- HAR 1.2 импорт: все записи в исходном порядке, тела запросов и ответов,
  `base64`-тела помечаются, а не портятся, HTTP/2 псевдо-заголовки отбрасываются
  с сохранением `httpVersion`, WebSocket-сообщения из `_webSocketMessages`.
- Разбор SSE на кадры: LF и CRLF, `data:` без пробела, многострочные `data`,
  comment-кадры (heartbeat — это сигнал), незавершённый последний кадр.
- `omniproxy capture import <file.har> --provider <id> --scenario <name>`.
- Локальный сырой кэш `~/.omniproxy/tmp` с TTL 1 час и правами 600 там, где
  платформа их соблюдает.

**Критерий приёмки выполнен:** число записей в бандле совпадает с числом записей
в HAR, SSE-ответ разложен на кадры, юнит-тесты на HAR-фикстуре в репозитории.
55 новых тестов (37 capture + 12 cli + 6 schema), все зелёные.

Решения, принятые по ходу и отличающиеся от черновика:
1. **Заголовки — упорядоченные пары, а не словарь + отдельный `headerOrder`.**
   Словарь теряет повторы (`set-cookie` приходит несколько раз), а два параллельных
   поля могут разойтись. `03-interfaces.ts` поправлен под реализацию.
2. **Тайминги кадров nullable.** HAR хранит поток одной строкой; выдумывать время
   прибытия кадра нельзя. `at: null` — честный ответ, живой рекордер (PR-7) заполнит.
3. **Импортёр ничего не фильтрует.** Телеметрия и статика попадают в бандл наравне
   с API-вызовами: решать, что шум, — работа анализатора (PR-3), и он сможет решать
   честно только если до него ничего не выбросили.
4. **Отсутствующее тело ответа — предупреждение, а не тишина.** HAR, экспортированный
   без содержимого, — самая частая причина бесполезного захвата. Теперь об этом
   сообщается сразу, с указанием, что переэкспортировать.
5. **Записанный бандл помечается `sanitized: false`** и кладётся только в локальный
   кэш с TTL. Гейт на запись в `fixtures/` появится в PR-2 вместе с самим санитайзером.

### PR-2 — выполнен (2026-08-27)
Санитайзер и гейт на запись фикстур.

Сделано:
- Детекторы: cookie по структуре заголовка, `set-cookie`, `authorization` (с сохранением
  схемы), список секретных заголовков, JWT по форме, e-mail, значения по имени ключа
  (`token`, `password`, `signature`, `api_key`, …) в JSON и form-urlencoded,
  query-параметры с секретными именами, высокоэнтропийные значения.
- Стабильные плейсхолдеры `{{redacted:<kind>:<n>}}`: одно и то же значение всегда даёт
  один и тот же плейсхолдер. Это сохраняет граф зависимостей для анализатора —
  «id из ответа A встречается в запросе B» остаётся верным и после редактирования.
- Замена в две фазы (сначала детект по всему бандлу, потом замена), поэтому форматирование
  тел сохраняется побайтово: пересериализация JSON изменила бы пробелы и порядок ключей,
  а фикстура ценна именно тем, что она — то, что прислал провайдер.
- Структура сохраняется: имена cookie, атрибуты `Set-Cookie`, схема `Bearer`,
  идентификаторы сессий и чатов остаются читаемыми.
- `writeFixture` — гейт: отказ при `sanitized !== true` **и** независимая повторная
  проверка готового текста на «формы» секретов. Флагу не верим.
- `omniproxy capture sanitize <bundle.json> [--out <path>]`, по умолчанию пишет в
  `~/.omniproxy/providers/<id>/fixtures/` — сразу в раскладку пользовательского модуля.

**Критерий приёмки выполнен:** тест «бандл с живыми cookie и JWT → в сохранённом файле
ни одного исходного значения» проходит; grep-гейт в CI зелёный на всём дереве.
133 теста (41 legacy, 6 schema, 66 capture, 20 cli).

Два бага, пойманных собственными тестами при написании:
1. **Короткий секрет в теле не заменялся.** Глобальная замена по литералу требует
   длины ≥ 8, иначе cookie `lang=en` превратил бы каждое «en» в захвате в плейсхолдер.
   Но `"password":"hunter2"` — 7 символов, и он утекал. Решение: короткие значения
   заменяются только там, где они ограничены как целое значение — в кавычках JSON или
   как поле формы целиком. Никогда как голая подстрока.
2. **Санитайзер не был идемпотентен.** На втором проходе он принимал собственные
   плейсхолдеры за секреты, перенумеровывал их и портил фикстуру. Теперь плейсхолдеры
   распознаются и не редактируются повторно.

### PR-3 — выполнен (2026-08-27)
Анализатор захвата и сравнение двух прогонов.

Сделано:
- **Классификация с обоснованием.** Каждый вызов получает `classification` **и список
  причин**. Классификация — подсказка человеку, а не приговор: анализатор, который
  прячет свои рассуждения, невозможно отлаживать в три часа ночи, когда провайдер сломался.
- Правила: preflight, известные телеметрические хосты и пути, статика по mime и
  расширению, WebSocket-апгрейд, SSE, multipart/бинарная загрузка, повторяющийся GET
  с меняющимся ответом → poll, `set-cookie` → auth, ответ, значение которого
  используется дальше → session.
- **Граф потока значений.** Ищем значения из ответов в последующих запросах: URL,
  заголовки, тело (с точным JSON-путём). Это то, что превращает плоский список в
  последовательность и что в PR-5 станет `{{state.sessionId}}`.
- Отсечка вездесущих значений: то, что встречается больше чем в половине запросов, —
  не зависимость, а константа вроде `application/json`.
- **Медиа-ответ считается артефактом только если на него сослался предыдущий вызов API.**
  Иначе это логотип, а не результат генерации. Различить их иначе нечем.
- **Сравнение двух захватов** одного сценария → `volatileFields`: изменившиеся
  query-параметры, заголовки, сегменты пути и пути в JSON-теле.
- `omniproxy capture analyze <bundle> [--compare <other>] [--json]`.

**Критерий приёмки:** выполнен на эталонном захвате в репозитории — цепочка
`session → send` восстановлена, идентификатор чата прослежен из ответа в URL следующего
запроса, телеметрия и статика отложены. **Критерий на живом DeepSeek остаётся открытым**
— захвата нет (риск R-11), это единственная невыполненная часть плана фазы 1.
172 теста (41 legacy, 8 schema, 98 capture, 26 cli).

Два решения, принятых по ходу:
1. **Сопоставление записей в два прохода.** Тест поймал дыру: идентификатор **в пути**
   (`/task/111` против `/task/222`) — самый частый случай для job-провайдеров — приводил
   к тому, что записи не сопоставлялись вовсе, и искомая переменная становилась
   невидимой именно потому, что она переменная. Теперь сначала точное совпадение
   эндпоинта, и только оставшееся сопоставляется по *форме* пути с подстановкой
   id-подобных сегментов. Нормализация сознательно узкая: `v1` и `completions` обязаны
   выжить, иначе спарятся разные эндпоинты и диф выдумает несуществующую волатильность.
2. **Анализ работает на санитизированных бандлах.** Отдельный тест: связь через
   отредактированный токен сохраняется, потому что PR-2 даёт одному значению один
   стабильный плейсхолдер. Если бы редактирование рвало граф, фикстуры были бы
   бесполезны для анализа.

`packages/engine-declarative`: JSONPath-подмножество, шаблоны, реестр трансформов,
фрейминг потоков, загрузчик деклараций, исполнитель потока. **297 тестов** в проекте
(41 legacy, 8 schema, 98 capture, 26 cli, 165 движок), все зелёные на Windows.

**Golden-тест против legacy.** `legacy/server.js` экспортирует `rebuildFragmentText`
и `applyResponsePatchOperations` через `__test`. Поэтому эталон в
`test/deepseek-parity.test.ts` — не мои ожидания, выведенные чтением кода, а сам
рабочий код: цикл `readDeepSeekResponse` переписан вокруг этих функций и запускается
на тех же кадрах, что и новый фреймер. Тринадцать сценариев плюс проверка на **каждой**
границе чанка от 1 до 40 байт. Это прямой ответ на риск R-15: заявление «декларация
плюс общий код делают то же, что рукописный адаптер» теперь либо подтверждено, либо
падает в CI.

Четыре дефекта, которые нашли именно тесты, а не чтение:

1. **Проверка хоста стояла после отправки запроса.** В `runStep` порядок был
   `buildRequest → http.request → assertAllowedHost`. То есть чужая декларация успела
   бы отправить cookie на свой хост, и только потом получила бы отказ. Проверка
   поднята выше запроса; тест утверждает, что клиент не получил *ни одного* вызова.
2. **Отсутствующее значение было неотличимо от ошибки.** `parent_message_id` первого
   сообщения отсутствует законно, а движок отказывался собирать запрос. Появились две
   формы, обе — данные: `{{x?}}` (поле выбрасывается) и `{{x|null-if-empty}}` (уходит
   JSON `null`). Строгость по умолчанию сохранена: молча пустой плейсхолдер — это
   безликий 400 через час.
3. **Нестримящий провайдер не мог отдать текст.** `emitNonStreamed` читал `stream.map`,
   которого у такого объявления нет. Добавлен блок `response` с той же картой — иначе
   сервис, отвечающий одним телом, пришлось бы писать кодовым адаптером ради двух
   JSONPath, то есть ровно то, чего движок должен избегать.
4. **`response/status` не обрабатывался.** Legacy по нему выставляет причину
   остановки — единственный сигнал о фильтрации на этом провайдере. Найдено сравнением
   с эталоном, а не чтением.

Ограничение, зафиксированное честно: тест PoW работает против **поддельного** WASM,
говорящего на том же ABI wasm-bindgen (бамп-аллокатор, теневой стек, i32-статус и
f64-ответ по указателю). Он проверяет арифметику указателей и формат заголовка —
то, что ломается молча, — но не то, что настоящий модуль решает настоящую задачу.
Это остаётся вопросом канарейки, а не модульного теста.

### PR-5 — выполнен (2026-08-27): закрытие R-11

Три новых пакета и первая настоящая декларация провайдера. **377 тестов** в проекте
(41 legacy, 8 schema, 98 capture, 26 cli, 166 движок, 15 симулятор, 23 сквозных),
все зелёные.

- `packages/transport` — `fetchHttpClient` (сеть), `recordingHttpClient` (пишет
  `CaptureBundle` из любого потока, который прошёл через него), `replayHttpClient`
  (отвечает из бандла, отказывается выдумывать отсутствующий обмен).
- `packages/provider-sim` — локальный сервер, говорящий на протоколе DeepSeek Web, и
  настоящий модуль WebAssembly, собранный побайтно (ADR-0007).
- `providers/deepseek-web/provider.yaml` — декларация, статус `unverified`.

**R-11 снижен с БЛОКЕРА до СРЕДНЕГО.** Конвейер прогоняется целиком на трафике,
который реально прошёл через сокет: движок → сокет → запись → санитизация → анализ →
воспроизведение, и воспроизведённый прогон выдаёт тот же текст, что живой. Открытым
остаётся вопрос свежести живого сервиса — вопрос канарейки, не конвейера.

Четыре дефекта, найденных прогоном, а не чтением:

1. **Конверт ошибки внутри HTTP 200 не проверялся.** DeepSeek сообщает об исчерпанной
   квоте кодом `40303` в JSON со статусом 200 вместо потока. Правила ошибок применялись
   только при `status >= 400`, и пользователь получал «провайдер не прислал текста».
2. **Трансформ качал WASM мимо проверки хостов и мимо записи.** `wasmUrl` в декларации
   был каналом утечки, которого не видела ни одна проверка, и дырой в записи ровно там,
   где происходит анти-бот работа. Теперь `fetchBytes` строит исполнитель поверх
   собственного HTTP-клиента, с проверкой хоста.
3. **Бинарные тела портились при записи.** WASM, декодированный как UTF-8, теряется
   безвозвратно. Записывающий клиент хранит нетекстовые тела в base64 — поле
   `bodyEncoding` в схеме было для этого с самого начала.
4. **`.wasm` попадал в предлагаемый поток вместо шума.** Анализатор теперь относит его
   к статике: декларация достаёт модуль трансформом, а не шагом.

Ограничение, зафиксированное честно: симулятор верен `legacy/server.js`, а не живому
сервису. Ни один статус выше `unverified` на прогоне против симулятора не выставляется.

### PR-6 — выполнен (2026-08-27): модули провайдеров становятся вещью, а не обещанием

**399 тестов** (41 legacy, 8 schema, 98 capture, 166 движок, 15 симулятор, 23 сквозных,
48 CLI), все зелёные.

`packages/engine-declarative/src/discovery.ts` — поиск модулей по ADR-0003. Порядок:
`--provider-dir` → `$OMNIPROXY_PROVIDER_PATH` → `~/.omniproxy/providers/` → `providers/`
в репозитории. Каталоги пользователя стоят **раньше** наших намеренно: перекрыть
поставляемого провайдера своей правленой копией — поддерживаемое действие, а не
случайность, которую надо предотвращать.

Три свойства, ради которых всё это и написано, каждое с тестом:

- модуль, написанный посторонним, находится ровно так же, как наш;
- модуль пользователя перекрывает наш с тем же id;
- **сломанный модуль не уносит с собой остальные.** Это разница между «одному
  провайдеру нужно внимание» и «шлюз лежит».

Новые команды:

- `omniproxy provider list` — что нашлось и откуда, с пометками про адаптер и
  предупреждения.
- `omniproxy provider validate [<id>]` — ошибки отдельно от предупреждений.
  Предупреждения никогда не блокируют: автор знает свой сервис лучше этого списка.
- `omniproxy capture record <id> --auth <file.json>` — прогоняет поток по-настоящему и
  пишет бандл. Раньше сообщения об ошибках движка советовали эту команду, а команды не
  было; теперь совет честный.

Деталь, которую стоит держать в голове: `capture record` пишет бандл **и при провале
потока**, помечая причину в `notes`. Запись упавшего прогона — обычно самая ценная:
именно она показывает, что сервис сказал, когда перестал работать.

### PR-7 — выполнен (2026-08-27): генератор черновика декларации

**422 теста** (41 legacy, 8 schema, 121 capture, 166 движок, 15 симулятор, 23 сквозных,
50 CLI), все зелёные. Конвейер онбординга §8 замкнут: `record → sanitize → analyze →
draft`.

`omniproxy provider draft <bundle>` превращает разобранный захват в `provider.yaml`.
Правило одно и жёсткое: **в файл попадает только то, что было в записи.** Где запись
молчит — стоит `# TODO(capture):`, а не правдоподобная подстановка. Догадка и факт
через три недели неотличимы, и именно так декларация начинает врать о провайдере.

Три места, где генератор мог соврать красиво, и что сделано вместо этого:

1. **Заголовок, меняющийся от запроса к запросу** — записанный PoW-блоб выглядит
   авторитетно и будет 403-ить вечно. Значение не пишется никогда: пишется
   `'{{vars.TODO}}'`, комментарий «этот заголовок менялся, ему нужен трансформ» и
   *описание формы* значения (`base64, 320 символов`) — читателю нужна форма, чтобы
   выбрать трансформ, а не само значение, которое может оказаться подписью.
2. **Неопознанный вызов перед отправкой** — молча выбросить его было бы худшим из
   возможных отказов: черновик выглядел бы законченным, а провайдер отвечал бы 403,
   потому что исчез шаг, добывающий токен. Такие вызовы попадают в `flow.prepare` с
   вопросом «что это за вызов?».
3. **Формы ошибок** — успешная запись их не содержит, поэтому вместо выдуманных правил
   стоит указание записать сессию с исчерпанным лимитом и с протухшим логином.

Черновик всегда выходит со статусом `needs-capture`: поднять статус — решение
человека, а не побочный эффект генерации. Сам сгенерированный файл прогоняется через
валидатор перед выдачей — черновик, который не парсится, это наша ошибка, а не работа
читателя (нашлось так: значение заголовка `20241129.1` YAML читает как число).

Первое измерение риска R-2 записано в `00-risks.md`.

### PR-8 — выполнен (2026-08-27): шлюз, пул аккаунтов, `omniproxy serve`

**610 тестов** (41 legacy, 8 schema, 121 capture, 166 движок, 15 симулятор,
23 сквозных, 91 диалект OpenAI, 68 CLI, 77 шлюз), все зелёные.

`packages/gateway` — HTTP-поверхность. В ней нет ни одного `if (provider === …)`
(§12.3): имя модели резолвится в декларацию, декларация уходит в движок, UMS-события
уходят в диалект.

```
POST /v1/chat/completions   потоково и нет
GET  /v1/models             все алиасы, полные и короткие
GET  /health                что загружено и как чувствуют себя аккаунты
```

**Маршрутизация.** Принимаются две формы: `deepseek-chat` и
`deepseek-web/deepseek-chat`. Полная существует потому, что короткая перестаёт быть
однозначной ровно в тот момент, когда два провайдера объявят один алиас, — а они
объявят, «default» назовут все. При неоднозначности маршрутизатор отвечает 409 и
перечисляет полные имена **вместо того, чтобы выбрать один**: запрос, обслуженный не
тем провайдером, — это неправильный ответ, выглядящий правильным. По той же причине
`/v1/models` не показывает короткое имя, которое был бы вынужден отвергнуть; тест
проверяет, что каждое перечисленное имя действительно резолвится.

**Состояние.** Его нет — ADR-0008, риск R-6 закрыт. Каждый запрос открывает свою
upstream-сессию, вся переписка склеивается в промпт форматом `legacy/server.js`
(формат ролевых меток — это поведение модели, а не оформление; на этом стоит golden-тест
из PR-4). Ответ становится функцией от запроса и ничего больше.

**Пул аккаунтов.** Один аккаунт — вырожденный случай, а не отдельная ветка (ADR-0004):
в `accounts.ts` нет `if (accounts.length === 1)`. Переход на другой аккаунт разрешён
только **до фиксации ответа** — то есть пока провайдер не прислал ничего, кроме
`start`/`warning`. До этой точки провал не стоил ничего, и именно там и появляются все
ошибки, ради которых ретрай нужен: протухший токен, лимит, исчерпанная квота. После —
сообщение уже списано, и второй заход списал бы второе.

Ради этого в шлюзе есть `commit()`: он читает поток ровно настолько, чтобы понять,
началось ли что-то, и **воспроизводит прочитанное** перед остатком, так что вызывающий
видит ту же последовательность событий, как если бы в неё никто не заглядывал.

**Три места, где легко соврать клиенту, и что сделано вместо этого:**

1. **Ошибка посреди потока.** Первый записанный байт фиксирует статус 200 — поздней
   ошибке уже некуда деться. Она уходит финальным чанком с кодом и `action`. Разница
   между «rate limited, возьмите другой аккаунт» и молча оборванным ответом, который
   любой клиент показывает как «модель замолчала».
2. **Ошибка до первого байта.** Ничего ещё не отправлено — значит честный ответ это
   429/401, а не 200 с ошибкой, закопанной в чанк. Тест на обе стороны границы.
3. **`/health` про непроверенного провайдера.** Статус печатается ровно как объявлен
   (`unverified`), и «нет аккаунта» видно до первого упавшего запроса (§12.10).

**Доступ.** Привязка по умолчанию — loopback. Не-loopback без `--api-key`
**отклоняется**, а не сопровождается предупреждением: предупреждение при старте
читается один раз и уезжает вверх, а цена пропущенного — чужие аккаунты. С ключом —
пожалуйста, общий шлюз на команду это ровно тот мультиарендный сценарий, который мы
обещали не запрещать. Сравнение ключа — `timingSafeEqual`. CORS отражает только
loopback-origin: wildcard дал бы любой странице в интернете тратить аккаунты
пользователя через его же машину.

**Что шлюз пока не делает** (честный список, §12.5): нет диалектов Anthropic и Gemini,
нет `/v1/capabilities`, нет очереди и конкурентности по каналам, нет канареек,
нет хранилища учёток (`--accounts <file.json>` читает открытый JSON — шифрование это
отдельный PR, и до него файл лежит там, куда его положил пользователь).

**Живой DeepSeek по-прежнему не проверен.** Всё выше прогоняется против симулятора из
ADR-0007 на настоящих сокетах — это закрывает вопрос конвейера, а не вопрос свежести.
Статус провайдера остаётся `unverified`, пока кто-нибудь не запишет
`omniproxy capture record` против chat.deepseek.com своим аккаунтом.

### PR-9 — выполнен (2026-08-27): `concurrency` перестал быть враньём

**631 тест** (+21 к PR-8), все зелёные.

`channels[].concurrency` лежало в схеме и в документированном формате `provider.yaml` с
самого начала, с подписью «одновременных запросов на аккаунт», и **не применялось
нигде**. Декларация, объявляющая ограничение, которого никто не соблюдает, — это
декларация, которая врёт (§12.5), и последствие тут не теоретическое: веб-чат,
рассчитанный на один запрос за раз, получив три, либо отвечает на один из них
неправильно, либо приводит к бану аккаунта.

`packages/gateway/src/gate.ts` — ворота на **аккаунт и канал**, а не на провайдера.
Два аккаунта по одному запросу дают два запроса; ради этого пул и нужен. Тест на это
есть, и он проверяет реальное перекрытие по журналу симулятора, а не по таймеру.

Четыре решения, каждое про «не подвести», а не про «быстрее»:

- **Слот держится до конца ответа, включая поток.** Отдать его раньше — значит
  разрешить второй запрос, пока первый ещё говорит, то есть ровно то, что декларация
  запрещает. Отдаётся в `finally`, поэтому путь ошибки отдаёт его так же, как путь
  успеха; потерянный на ошибке слот — это аккаунт, который навсегда выглядит занятым.
- **Слот передаётся следующему в очереди напрямую**, а не освобождается. Между
  освобождением и повторным захватом новоприбывший обгонял бы всю очередь.
- **Очередь ограничена с двух сторон.** Без предела на длину замедление провайдера
  превращается в проблему с памятью; без дедлайна — в клиента, который висит вечно и не
  может понять, происходит ли хоть что-то. Оба отказа называют ожидание и говорят, что
  делать.
- **Двойной release считается за один.** Иначе выдаётся слот, которого нет, а
  перепродажа обнаруживается только тогда, когда жалуется провайдер.

Пул теперь предпочитает незанятый аккаунт занятому (совет, а не правило: если заняты
все, запрос всё равно уходит и встаёт в очередь у ворот). `/health` показывает, что
выполняется и что ждёт.

### PR-10 — выполнен (2026-08-27): второй диалект, и слой, который сделал его дешёвым

**705 тестов** (+74 к PR-9), все зелёные.

Шлюз теперь отвечает на два клиентских протокола сразу, поверх одних и тех же
провайдеров и одних и тех же аккаунтов:

```
POST /v1/chat/completions   OpenAI Chat Completions
POST /v1/messages           Anthropic Messages
```

**Сначала — слой, потом диалект.** `packages/umr` — универсальный запрос: одна форма
диалога, в которую переводит себя каждый публичный протокол, плюс склейка в промпт и
разбор tool-разметки из обычного текста. Без него формат промпта зависел бы от того,
каким SDK случайно воспользовался вызывающий, а правка рендеринга tool-результата
делалась бы трижды — и делалась бы дважды, а третий случай нашёл бы пользователь.

Перенос проверяется тем, что 91 тест диалекта OpenAI — включая golden-паритет с
`legacy/server.js` — прошёл **без единого изменения**: 60 остались на месте, 31
переехал вместе с парсером. Ровно то доказательство, которое нужно от рефакторинга.

**Что диалект обязан предоставить** (`packages/gateway/src/dialect.ts`): как прочитать
запрос, как записать ответ, как сформулировать отказ. Всё остальное — маршрутизация,
аккаунты, ворота конкурентности, правило ретрая, движок — общее. Добавление Gemini или
собственного протокола пользователя не трогает цикл запроса; если бы потрогало,
универсальные слои не отрабатывали бы свою стоимость. Это измеримая форма §4.

**Три места, где Anthropic отличается настолько, что небрежный порт теряет данные:**

1. **`system` — поле, а не роль.** Принять роль `system` в `messages` значило бы молча
   её потерять; схема её отвергает.
2. **Tool-результат живёт блоком внутри user-хода.** Оставить его там — заставить
   модель читать вывод собственного инструмента как реплику человека. Конвертер
   поднимает его в отдельное сообщение и сохраняет порядок, если ход смешанный.
3. **`max_tokens` обязателен.** Об этом сказано отдельной фразой: тот, кто переносит
   код с OpenAI, спотыкается об это первым, и `messages.0: Required` отправило бы его
   искать не туда.

**Поток Anthropic структурнее.** Контент приходит нумерованными блоками, которые
открывают, наполняют и закрывают, а причина остановки едет отдельным событием. Клиент,
не дождавшийся `content_block_stop`, ждёт вечно, поэтому тесты проверяют
последовательность событий, а не только текст.

**`thinking` без `signature`.** Настоящий API подписывает блок размышления; мы подписать
не можем. Блок отдаётся без подписи, и это записано и здесь, и в коде: показывать его
можно, отправлять обратно в api.anthropic.com — нельзя. Придумать значение поля было бы
хуже.

**`/v1/models` отвечает обоим.** Оба протокола объявляют этот путь и расходятся в именах
полей, поэтому каждая запись несёт оба набора. Это надмножество, а не выдумка: каждое
поле говорит правду, и оба клиента находят то, что ищут, вместо того чтобы один из них
получал 404.

**Ключ принимается в обоих видах** — `Authorization: Bearer` и `x-api-key`, потому что
OpenAI-клиенты шлют первое, а Anthropic-клиенты второе. Отказ одному из них обесценил бы
половину смысла двух диалектов.

Ворота конкурентности и пул — общие: два эндпоинта не складываются в двойную квоту у
провайдера. На это есть тест.

### PR-11 — выполнен (2026-08-27): третий протокол, Gemini

**779 тестов** (+74 к PR-10), все зелёные. Шлюз принимает запросы в трёх форматах:

```
POST /v1/chat/completions                    OpenAI Chat Completions
POST /v1/messages                            Anthropic Messages
POST /v1beta/models/<model>:generateContent  Gemini (и :streamGenerateContent)
```

Проверка, ради которой всё и строилось (§4): диалект Gemini добавил **три файла и одну
строку в таблице маршрутов**. Цикл запроса — маршрутизация, аккаунты, ворота, ретрай,
движок — не изменился ни на строку. Тест сравнивает промпт, дошедший до провайдера с
трёх эндпоинтов, побайтно: одинаковый.

**Что пришлось выучить циклу запроса.** Ровно одно: Google кладёт модель и операцию в
URL, а не в тело. Таблица диалектов стала списком матчеров, и `plan()` получил
необязательный контекст маршрута. Полное имя модели содержит слэш
(`/v1beta/models/deepseek-web/deepseek-chat:generateContent`), так что сегмент пути
нельзя прочитать как одно слово — на это есть тест.

**Отличия Gemini, каждое со своим тестом:**

- роль ассистента называется `model`, отсутствующая роль означает `user`;
- результат функции — часть `functionResponse` внутри user-хода, и ключ у него **имя
  функции**, а не id вызова: другого способа сопоставить результат с вызовом у модели
  нет;
- инструменты — список списков (`tools[].functionDeclarations[]`);
- ручки генерации лежат во вложенном `generationConfig`.

**У потока Google нет сентинела.** Клиент узнаёт, что поток кончился, а не оборвался,
только по `finishReason` в последнем чанке — поэтому он там всегда, включая случай, когда
причина это ошибка: последний чанк несёт `finishReason: OTHER` и объект ошибки рядом.
Альтернатива — молча оборванный поток, который любой клиент показывает как «модель
замолчала».

**`safetyRatings` всегда пуст.** Мы не запускали классификатор, и напечатать оценки,
которых никто не считал, — это выдуманное измерение, что хуже пустого списка.

**`countTokens` отвечает оценкой и говорит, что это оценка.** В теле стоит
`omniproxy.estimated: true` и `method: "characters/4"`. Отказать было можно, но это
ломает всякого клиента, который считает перед отправкой; §12.10 работает в обе стороны —
не преувеличивать готовность и не притворяться, что работающая функция отсутствует.
Ни один провайдер при этом не трогается и ни одно сообщение не тратится.

**Ключ принимается во всех четырёх видах**: `Authorization: Bearer`, `x-api-key`,
`x-goog-api-key` и `?key=`. Последнее — дизайн Google, а не наш; параметр принимается,
чтобы работали их SDK, а от того, чтобы ключ в URL стал слабым звеном, защищает всё тот
же отказ `serve` слушать не-loopback без ключа.

`/v1beta/models` — отдельный путь со своей формой ответа; `/v1/models` остался общим
надмножеством для двух других клиентов.

### PR-12 — выполнен (2026-08-27): четвёртый протокол, Ollama

**839 тестов** (+60 к PR-11), все зелёные. Шлюз принимает запросы в четырёх форматах:

```
POST /v1/chat/completions                    OpenAI Chat Completions
POST /v1/messages                            Anthropic Messages
POST /v1beta/models/<model>:generateContent  Gemini (и :streamGenerateContent)
POST /api/chat, POST /api/generate           Ollama (NDJSON)
```

Ollama взят не ради счётчика протоколов. На нём построена целая экосистема локальных
инструментов, которые не умеют говорить ни на чём другом, и направить такой инструмент
на веб-интерфейс провайдера — ровно то, ради чего проект существует.

**Что он проверил в абстракции.** Первые три диалекта — все SSE. Если бы `DialectHooks`
был случайно скроен под server-sent events, это вскрылось бы только здесь. Не вскрылось:
`respond()` получает поток UMS и сам решает, во что его писать, так что NDJSON-писатель
живёт в `packages/gateway/src/ollama.ts` и больше нигде. Цикл запроса — маршрутизация,
аккаунты, ворота, ретрай, движок — снова не изменился ни на строку. Тест сравнивает
промпт, дошедший до провайдера со всех четырёх эндпоинтов, побайтно: одинаковый.

**Две привычки Ollama противоположны всем остальным, и обе были бы тихими багами:**

- **`stream` по умолчанию `true`.** У всех остальных — `false`. Клиент, который не
  прислал поле, просит поток, и один JSON-объект в ответ оставляет его ждать строк,
  которые не придут. Отдельный тест на запрос без поля `stream`.
- **формат — NDJSON, а не SSE**: один JSON-объект на строку, без префикса `data:` и без
  пустой строки-разделителя. Тест проверяет, что в теле нет `data: `.

**Баг, который нашёл тест, а не пользователь.** Закрывающая запись потока несла полный
текст ответа — она строится тем же `buildOllamaResponse`, что и непотоковый ответ.
Клиенты Ollama склеивают содержимое всех записей подряд, так что пользователь увидел бы
ответ дважды. Теперь закрывающая запись несёт причину и счётчики, а содержимое в ней
пустое.

**Поток всегда заканчивается записью `done`,** включая путь ошибки. Клиент, который ждёт
`done`, при оборванном сокете ждёт вечно; если до ошибки ещё ничего не отправлено, шлюз
успевает ответить настоящим статусом, а если отправлено — приходит `done` с
`done_reason: "error"` и текстом.

**Честность в служебных эндпоинтах (§12.10):**

- `/api/tags` отдаёт `size: 0` и `digest: ""`. Файла на диске нет, а правдоподобный
  digest был бы выдуманным фактом о несуществующем объекте.
- `/api/show` печатает `omniproxy.status` ровно так, как написано в декларации, и **не**
  сообщает длину контекста: против живого сервиса её никто не мерил, а число здесь
  клиент начал бы планировать.
- `/api/version` отвечает `0.1.0-omniproxy`, а не версией Ollama, которой мы не
  являемся.

**Мелочи, каждая со своим тестом:** аргументы tool-call у Ollama — объект, а не строка,
как у OpenAI; `num_predict: -1` означает «без ограничения» и не является бюджетом
токенов; `/api/generate` не имеет конверта сообщения и tool-calling, поэтому текст там
возвращается как пришёл; картинки называются, но не передаются — текстовый канал не
примет мегабайты base64, а модель, которой сказали про вложение, может ответить, что не
видит его, и это несравнимо лучше, чем ответ так, будто вложения не было.

Ворота конкурентности и пул аккаунтов — общие на все четыре эндпоинта. На это есть тест,
который шлёт четыре запроса разными протоколами разом.

### PR-13 — выполнен (2026-08-27): диалект, которого у нас нет

**868 тестов** (+29 к PR-12), все зелёные. Пятый протокол больше не наша задача.

Просьба звучала как «пусть прокси принимает любые виды запросов — не только OpenAI, а и
Anthropic, Gemini и другие». Первые три — это PR-10 и PR-11, четвёртый — PR-12. Но
«и другие» — список без конца, и честный ответ на него не «угадаем пятый», а «сделаем
так, чтобы пятый писали без нас».

**Что изменилось.** `DialectPlugin` — это весь контракт монтирования: имя, хуки,
матчер пути, необязательные `paths` для человекочитаемого 404 и необязательный `side`
для эндпоинтов, которые не доходят до провайдера. Встроенные четыре переписаны на него
и монтируются **тем же способом**, что пользовательский. Это не оформление, а
проверяемое свойство: привилегированной ветки, до которой плагин не дотягивается, в
`server.ts` не осталось — `/api/tags`, `/api/show`, `/api/version`, `/v1beta/models` и
`countTokens` переехали в `side` своих диалектов.

**Пользовательские плагины монтируются перед встроенными.** Плагин, заявивший
`/v1/chat/completions`, заменяет наш OpenAI-эндпоинт, а не проигрывает ему. Шлюз ваш;
в лог пишется одна строка о перекрытии, и на этом всё (`06-hackability-charter.md`).
На оба факта есть тесты.

**Тело запроса читается один раз.** `side`-обработчик, заглянувший в тело, раньше
съел бы поток, который нужен циклу запроса, — и симптом (пустой диалог, но только когда
смонтирован некий плагин) искался бы полдня. Теперь чтение общее и запомненное, и на это
есть отдельный тест с плагином, который читает каждое тело и не отвечает ни на что.

**Загрузка с диска (`--dialect <файл|каталог>`).** Неявно не загружается ничего: ни
рабочий каталог, ни `node_modules`, ни «известная папка» — только названные пути.
Каталог читается на один уровень и сортируется, чтобы порядок перекрытий был одинаков на
Windows и на Linux (ADR-0005). Экспорт может называться `default`, `dialect` или
`plugin`. Сломанный файл называется и пропускается (I-1), `.ts` получает внятное «сначала
скомпилируйте», а не непонятную ошибку импорта. Плагин проверяется при старте, а не при
первом запросе: диалект без `respond()` должен падать с именем файла, а не посреди
чьего-то ответа.

**Про безопасность сказано прямо.** `--dialect` исполняет чужой JavaScript в процессе
шлюза, с его аккаунтами. При старте печатается одна предупреждающая строка — и дальше
делается то, что попросили.

Документация: `docs/omniproxy/07-writing-a-dialect.md` — контракт, полный рабочий пример
на сорок строк, список того, что делать не нужно, и таблица встроенных диалектов как
образцов. Тест, который держит эту дверь открытой, — `packages/gateway/test/plugin.test.ts`:
диалект, изобретённый прямо в тесте, получает тот же промпт у провайдера, тот же пул
аккаунтов и тот же переход на другой аккаунт, что и встроенные четыре.
