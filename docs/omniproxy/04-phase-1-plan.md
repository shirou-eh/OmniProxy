# Фаза 1 — конвейер захвата. План работ по PR

Цель фазы: доказать главную гипотезу проекта — **из захваченного трафика механически
получается работающая декларация**. Проверка на DeepSeek, для которого правильный ответ
уже известен (`server.js:529-676` + `docs/api-documentation.md`).

Порядок изменён относительно §8.2: CDP-рекордер идёт раньше расширения (риск R-1 —
MV3 не отдаёт тела ответов, расширению нужен `chrome.debugger`, это отдельная и более
дорогая работа).

---

## PR-0. Скелет монорепо и CI *(формально фаза 0, но фаза 1 без него не собирается)*

- pnpm workspaces + Turborepo, базовый `tsconfig` (strict, ESM, `NodeNext`), tsup, vitest.
- `packages/schema` с пустыми экспортами, `packages/capture`, `packages/testkit`.
- Текущий проект целиком переезжает в `legacy/` **без изменений** и продолжает
  запускаться командой `pnpm legacy:start`.
- CI: lint + typecheck + `vitest run` + запуск старых тестов `legacy/tests/unit.test.js`.

**Критерии приёмки:** `pnpm i && pnpm build && pnpm test` зелёные на чистой машине;
`pnpm legacy:start` поднимает текущий сервер и отвечает на `/health`; старые 735 строк
тестов проходят без правок.

## PR-1. Модель захвата и HAR-импорт

`packages/capture`:
- Zod-схема `CaptureBundle` / `CaptureEntry` (см. `03-interfaces.ts`) в `packages/schema`.
- Импорт HAR 1.2: разбор `log.entries`, восстановление `headerOrder` из исходного
  порядка, декодирование `content.text` с `base64`.
- Восстановление SSE: HAR хранит тело потока одной строкой — разбиваем на кадры по
  `\n\n`, сохраняем в `frames` (тайминги при импорте из HAR отсутствуют, помечаем `at: null`).
- CLI: `omniproxy capture import <file.har> --provider <id> --scenario <name>`.

**Критерии приёмки:** импорт HAR, сохранённого из DevTools на любом SSE-сайте,
даёт бандл, в котором количество entries совпадает с числом запросов в HAR,
а SSE-ответ разложен на кадры; юнит-тесты на фикстуре HAR в репозитории.

## PR-2. Санитайзер (блокирующее требование §8.4)

- Детекторы секретов: значения известных cookie-имён из декларации, `authorization`,
  `set-cookie`, JWT по форме, длинные hex/base64-значения (> 24 симв. и высокая
  энтропия), e-mail, телефоны, `user_id`-подобные поля.
- Замена на стабильные плейсхолдеры (`{{redacted:token:1}}`), запись соответствия
  **вида** секрета в `redactions` — без значений.
- Санитизация обязательна и неотключаема: `CaptureBundle.sanitized !== true` →
  запись на диск в `fixtures/` отклоняется.
- Отдельный «сырой» кэш живёт только в памяти процесса и в `.omniproxy/tmp` с
  правами 600 и TTL 1 час, в git не попадает (`.gitignore` + проверка в CI).

**Критерии приёмки:** тест «загрузить бандл с живыми cookie/JWT → в сохранённом файле
ни одного исходного значения»; grep-тест в CI, который валит сборку при обнаружении
похожего на секрет значения в `packages/providers/*/fixtures/**`.

## PR-3. Анализатор захвата

- Фильтрация шума: аналитика (белый список доменов + эвристики `/log`, `/track`,
  `/beacon`, `sentry`, `ga`), статика по mime и расширению, preflight `OPTIONS`.
- Классификация оставшихся вызовов в `CaptureEntry.classification` по признакам:
  наличие `set-cookie` → auth; ответ с идентификатором, который потом появляется в URL
  следующего запроса → session; `text/event-stream` → stream; повторяющийся GET с
  монотонно меняющимся телом → poll; `PUT` на другой хост с бинарным телом → upload;
  ответ с `video/*`, `image/*`, `audio/*` → artifact.
- Восстановление последовательности: граф зависимостей по «значение из ответа A
  встречается в запросе B».
- Diff между двумя бандлами одного сценария → заполнение `volatileFields`
  (это ровно те поля, которые в декларации станут `{{...}}`).

**Критерии приёмки:** на двух захватах DeepSeek анализатор находит цепочку
`create_pow_challenge → chat_session/create → chat/completion`, помечает
`chat_session_id` / `parent_message_id` / PoW-заголовок как volatile, а телеметрию
отбрасывает; результат проверяется юнит-тестом против ожидаемой цепочки.

## PR-4. Минимальный движок деклараций

`packages/engine-declarative` — ровно столько, чтобы сгенерированный черновик можно было
исполнить и проверить:
- шаблонизатор `{{...}}` с закрытым списком модификаторов;
- подмножество JSONPath для `extract` и `stream.map`;
- исполнитель `flow` для `createSession` / `send`, `HttpClient` через порт;
- парсеры framing: `sse`, `ndjson`, `json-patch` (нужен для DeepSeek);
- реестр transforms с первыми элементами: `uuid-v4`, `base64`, `json-stringify`,
  `hmac-sha256`, `deepseek-pow-v0` (обёртка над портированным `lib/pow.js`).

**Критерии приёмки:** движок исполняет вручную написанную декларацию DeepSeek против
replay-фикстуры и отдаёт тот же текст ответа, что и `legacy/server.js` на том же входе
(golden-тест, сравнение посимвольно, включая порядок reasoning/text-дельт).

## PR-5. Генератор черновика `provider.yaml`

- Из проанализированного бандла: `channels[0]` (base, статические заголовки, headerOrder,
  профиль отпечатка по User-Agent), `auth.harvest` (по именам cookie из `set-cookie`
  и заголовка `cookie`), `flow.createSession` / `flow.send` / `flow.poll`,
  `stream.format` + черновой `map` (по путям, где в кадрах меняется строковое значение),
  `errors` (по не-2xx ответам в бандле).
- Всё неразрешённое — в `notes` и в YAML-комментарии `# TODO(capture): ...`:
  необъяснимые заголовки, значения без источника в предыдущих ответах, PoW/подписи.
- Черновик всегда получает `status: needs-capture` и `class: unknown` — человек обязан
  проставить их руками.

**Критерии приёмки:** `omniproxy capture analyze` на бандле DeepSeek выдаёт YAML,
который после **не более чем 10 строк ручных правок** проходит `provider validate`
и golden-тест из PR-4. Число правок фиксируется в отчёте фазы — это и есть измерение
качества конвейера.

## PR-6. Replay-харнесс и контрактные тесты

`packages/testkit`:
- `ReplayHttpClient`: сопоставляет исходящий запрос с записью бандла (метод + путь +
  нормализованное тело), отдаёт записанный ответ и кадры с исходными таймингами.
- Несовпадение запроса — не «промах кэша», а падение теста с diff'ом (иначе тесты
  начинают лгать, риск R-7).
- Диффер схем: фактический JSON против записанного — список путей
  «появился / исчез / сменил тип», в человекочитаемом виде.
- `defineContractTest(providerId)` — один вызов на провайдера.

**Критерии приёмки:** контрактный тест DeepSeek проходит офлайн, без сети и без
аккаунта; искусственное изменение пути в фикстуре даёт понятный diff, а не стектрейс.

## PR-7. CDP-рекордер

`omniproxy capture record <provider>`:
- обобщение `scripts/deepseek_chrome_auth.js` (там уже есть запуск Chrome, CDP по
  WebSocket, `Runtime.evaluate`, `Network.getAllCookies`) — выносим в `packages/auth`
  общий CDP-клиент;
- подписка на `Network.requestWillBeSent` / `responseReceived` / `loadingFinished` /
  `getResponseBody` и, отдельно, `Network.eventSourceMessageReceived` для SSE
  (единственный способ получить кадры с таймингами);
- интерактивный сценарий: «войдите → выполните действие → Enter», на выходе — бандл,
  прогнанный через санитайзер;
- одновременно снимается credential (та же сессия) — авторизация и захват одним проходом.

**Критерии приёмки:** запись сценария на живом DeepSeek даёт бандл, из которого PR-5
генерирует черновик, проходящий golden-тест. **Этот критерий требует живого аккаунта
пользователя** (риск R-11) — до его выполнения фаза 1 считается незакрытой.

## Что фаза 1 НЕ делает

Ни ядра, ни роутера, ни протоколов, ни job-модели, ни новых провайдеров. Движок
деклараций пишется в объёме «достаточно для DeepSeek» и будет дополняться в фазе 2.
Старый `server.js` всё это время остаётся единственным рабочим сервером.

## Метрика успеха фазы

**Число ручных правок в сгенерированном черновике до прохождения golden-теста.**
≤ 10 строк — конвейер работает, идём в фазу 2. 30+ строк — гипотеза проекта не
подтвердилась, надо либо радикально усиливать анализатор, либо признать, что
адаптеры пишутся руками, и пересобирать план вокруг этого.

---

## Поправка после ADR-0003

Конвейер захвата с самого начала пишется как **пользовательский** инструмент, а не как
внутренний скрипт:

- `omniproxy capture record|import|analyze` принимают произвольный `<id>`, в том числе
  провайдера, которого нет в репозитории; результат кладётся в `~/.omniproxy/providers/<id>/`.
- Санитайзер (PR-2) и ограничение хостов (`allowedHosts`) — не «best practice», а условие
  того, что декларациями можно безопасно обмениваться.
- Диагностика в `provider try` пишется на языке автора модуля («JSONPath не нашёл поле,
  в ответе есть такое-то»), а не в терминах внутренних компонентов.

Загрузчик внешних модулей и граница доверия въезжают в фазу 2 вместе с реестром —
дописывать это после означает переделывать реестр.

### PR-1 — выполнен (2026-08-27)
`packages/capture` + `apps/cli`.

Сделано:
- `CaptureBundle` / `CaptureEntry` / `CaptureFrame` в `packages/schema` (zod).
- HAR 1.2 импорт: все записи в исходном порядке, тела запросов и ответов,
  `base64`-тела помечаются, а не портятся, HTTP/2 псевдо-заголовки отбрасываются
  с сохранением `httpVersion`, WebSocket-сообщения из `_webSocketMessages`.
- Разбор SSE на кадры: LF и CRLF, `data:` без пробела, многострочные `data`,
  comment-кадры (heartbeat — это сигнал), незавершённый последний кадр.
- `omniproxy capture import <file.har> --provider <id> --scenario <name>`.
- Локальный сырой кэш `~/.omniproxy/tmp` с TTL 1 час и правами 600 там, где
  платформа их соблюдает.

**Критерий приёмки выполнен:** число записей в бандле совпадает с числом записей
в HAR, SSE-ответ разложен на кадры, юнит-тесты на HAR-фикстуре в репозитории.
55 новых тестов (37 capture + 12 cli + 6 schema), все зелёные.

Решения, принятые по ходу и отличающиеся от черновика:
1. **Заголовки — упорядоченные пары, а не словарь + отдельный `headerOrder`.**
   Словарь теряет повторы (`set-cookie` приходит несколько раз), а два параллельных
   поля могут разойтись. `03-interfaces.ts` поправлен под реализацию.
2. **Тайминги кадров nullable.** HAR хранит поток одной строкой; выдумывать время
   прибытия кадра нельзя. `at: null` — честный ответ, живой рекордер (PR-7) заполнит.
3. **Импортёр ничего не фильтрует.** Телеметрия и статика попадают в бандл наравне
   с API-вызовами: решать, что шум, — работа анализатора (PR-3), и он сможет решать
   честно только если до него ничего не выбросили.
4. **Отсутствующее тело ответа — предупреждение, а не тишина.** HAR, экспортированный
   без содержимого, — самая частая причина бесполезного захвата. Теперь об этом
   сообщается сразу, с указанием, что переэкспортировать.
5. **Записанный бандл помечается `sanitized: false`** и кладётся только в локальный
   кэш с TTL. Гейт на запись в `fixtures/` появится в PR-2 вместе с самим санитайзером.

### PR-2 — выполнен (2026-08-27)
Санитайзер и гейт на запись фикстур.

Сделано:
- Детекторы: cookie по структуре заголовка, `set-cookie`, `authorization` (с сохранением
  схемы), список секретных заголовков, JWT по форме, e-mail, значения по имени ключа
  (`token`, `password`, `signature`, `api_key`, …) в JSON и form-urlencoded,
  query-параметры с секретными именами, высокоэнтропийные значения.
- Стабильные плейсхолдеры `{{redacted:<kind>:<n>}}`: одно и то же значение всегда даёт
  один и тот же плейсхолдер. Это сохраняет граф зависимостей для анализатора —
  «id из ответа A встречается в запросе B» остаётся верным и после редактирования.
- Замена в две фазы (сначала детект по всему бандлу, потом замена), поэтому форматирование
  тел сохраняется побайтово: пересериализация JSON изменила бы пробелы и порядок ключей,
  а фикстура ценна именно тем, что она — то, что прислал провайдер.
- Структура сохраняется: имена cookie, атрибуты `Set-Cookie`, схема `Bearer`,
  идентификаторы сессий и чатов остаются читаемыми.
- `writeFixture` — гейт: отказ при `sanitized !== true` **и** независимая повторная
  проверка готового текста на «формы» секретов. Флагу не верим.
- `omniproxy capture sanitize <bundle.json> [--out <path>]`, по умолчанию пишет в
  `~/.omniproxy/providers/<id>/fixtures/` — сразу в раскладку пользовательского модуля.

**Критерий приёмки выполнен:** тест «бандл с живыми cookie и JWT → в сохранённом файле
ни одного исходного значения» проходит; grep-гейт в CI зелёный на всём дереве.
133 теста (41 legacy, 6 schema, 66 capture, 20 cli).

Два бага, пойманных собственными тестами при написании:
1. **Короткий секрет в теле не заменялся.** Глобальная замена по литералу требует
   длины ≥ 8, иначе cookie `lang=en` превратил бы каждое «en» в захвате в плейсхолдер.
   Но `"password":"hunter2"` — 7 символов, и он утекал. Решение: короткие значения
   заменяются только там, где они ограничены как целое значение — в кавычках JSON или
   как поле формы целиком. Никогда как голая подстрока.
2. **Санитайзер не был идемпотентен.** На втором проходе он принимал собственные
   плейсхолдеры за секреты, перенумеровывал их и портил фикстуру. Теперь плейсхолдеры
   распознаются и не редактируются повторно.

### PR-3 — выполнен (2026-08-27)
Анализатор захвата и сравнение двух прогонов.

Сделано:
- **Классификация с обоснованием.** Каждый вызов получает `classification` **и список
  причин**. Классификация — подсказка человеку, а не приговор: анализатор, который
  прячет свои рассуждения, невозможно отлаживать в три часа ночи, когда провайдер сломался.
- Правила: preflight, известные телеметрические хосты и пути, статика по mime и
  расширению, WebSocket-апгрейд, SSE, multipart/бинарная загрузка, повторяющийся GET
  с меняющимся ответом → poll, `set-cookie` → auth, ответ, значение которого
  используется дальше → session.
- **Граф потока значений.** Ищем значения из ответов в последующих запросах: URL,
  заголовки, тело (с точным JSON-путём). Это то, что превращает плоский список в
  последовательность и что в PR-5 станет `{{state.sessionId}}`.
- Отсечка вездесущих значений: то, что встречается больше чем в половине запросов, —
  не зависимость, а константа вроде `application/json`.
- **Медиа-ответ считается артефактом только если на него сослался предыдущий вызов API.**
  Иначе это логотип, а не результат генерации. Различить их иначе нечем.
- **Сравнение двух захватов** одного сценария → `volatileFields`: изменившиеся
  query-параметры, заголовки, сегменты пути и пути в JSON-теле.
- `omniproxy capture analyze <bundle> [--compare <other>] [--json]`.

**Критерий приёмки:** выполнен на эталонном захвате в репозитории — цепочка
`session → send` восстановлена, идентификатор чата прослежен из ответа в URL следующего
запроса, телеметрия и статика отложены. **Критерий на живом DeepSeek остаётся открытым**
— захвата нет (риск R-11), это единственная невыполненная часть плана фазы 1.
172 теста (41 legacy, 8 schema, 98 capture, 26 cli).

Два решения, принятых по ходу:
1. **Сопоставление записей в два прохода.** Тест поймал дыру: идентификатор **в пути**
   (`/task/111` против `/task/222`) — самый частый случай для job-провайдеров — приводил
   к тому, что записи не сопоставлялись вовсе, и искомая переменная становилась
   невидимой именно потому, что она переменная. Теперь сначала точное совпадение
   эндпоинта, и только оставшееся сопоставляется по *форме* пути с подстановкой
   id-подобных сегментов. Нормализация сознательно узкая: `v1` и `completions` обязаны
   выжить, иначе спарятся разные эндпоинты и диф выдумает несуществующую волатильность.
2. **Анализ работает на санитизированных бандлах.** Отдельный тест: связь через
   отредактированный токен сохраняется, потому что PR-2 даёт одному значению один
   стабильный плейсхолдер. Если бы редактирование рвало граф, фикстуры были бы
   бесполезны для анализа.

`packages/engine-declarative`: JSONPath-подмножество, шаблоны, реестр трансформов,
фрейминг потоков, загрузчик деклараций, исполнитель потока. **297 тестов** в проекте
(41 legacy, 8 schema, 98 capture, 26 cli, 165 движок), все зелёные на Windows.

**Golden-тест против legacy.** `legacy/server.js` экспортирует `rebuildFragmentText`
и `applyResponsePatchOperations` через `__test`. Поэтому эталон в
`test/deepseek-parity.test.ts` — не мои ожидания, выведенные чтением кода, а сам
рабочий код: цикл `readDeepSeekResponse` переписан вокруг этих функций и запускается
на тех же кадрах, что и новый фреймер. Тринадцать сценариев плюс проверка на **каждой**
границе чанка от 1 до 40 байт. Это прямой ответ на риск R-15: заявление «декларация
плюс общий код делают то же, что рукописный адаптер» теперь либо подтверждено, либо
падает в CI.

Четыре дефекта, которые нашли именно тесты, а не чтение:

1. **Проверка хоста стояла после отправки запроса.** В `runStep` порядок был
   `buildRequest → http.request → assertAllowedHost`. То есть чужая декларация успела
   бы отправить cookie на свой хост, и только потом получила бы отказ. Проверка
   поднята выше запроса; тест утверждает, что клиент не получил *ни одного* вызова.
2. **Отсутствующее значение было неотличимо от ошибки.** `parent_message_id` первого
   сообщения отсутствует законно, а движок отказывался собирать запрос. Появились две
   формы, обе — данные: `{{x?}}` (поле выбрасывается) и `{{x|null-if-empty}}` (уходит
   JSON `null`). Строгость по умолчанию сохранена: молча пустой плейсхолдер — это
   безликий 400 через час.
3. **Нестримящий провайдер не мог отдать текст.** `emitNonStreamed` читал `stream.map`,
   которого у такого объявления нет. Добавлен блок `response` с той же картой — иначе
   сервис, отвечающий одним телом, пришлось бы писать кодовым адаптером ради двух
   JSONPath, то есть ровно то, чего движок должен избегать.
4. **`response/status` не обрабатывался.** Legacy по нему выставляет причину
   остановки — единственный сигнал о фильтрации на этом провайдере. Найдено сравнением
   с эталоном, а не чтением.

Ограничение, зафиксированное честно: тест PoW работает против **поддельного** WASM,
говорящего на том же ABI wasm-bindgen (бамп-аллокатор, теневой стек, i32-статус и
f64-ответ по указателю). Он проверяет арифметику указателей и формат заголовка —
то, что ломается молча, — но не то, что настоящий модуль решает настоящую задачу.
Это остаётся вопросом канарейки, а не модульного теста.
