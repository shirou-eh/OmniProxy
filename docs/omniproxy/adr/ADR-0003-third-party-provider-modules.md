# ADR-0003 — Пользовательские модули провайдеров (внешние, без форка)

- Статус: proposed
- Дата: 2026-08-27
- Контекст: требование, добавленное к промту. Пользователь должен иметь возможность
  сам подключить **любой** сервис — вышедшую вчера модель картинок, 3D-генератор,
  очередной чат — не трогая исходники OmniProxy и не дожидаясь релиза.

## Главное наблюдение

Это **не новая подсистема**. Конвейер §8 (захват → анализ → декларация → фикстуры →
канарейка) и трёхуровневая граница ADR-0002 уже описывают ровно эту работу — просто
адресатом до сих пор считался разработчик проекта. Разворачиваем конвейер к пользователю.

Отсюда следует, что развилка «встроенный провайдер против пользовательского» не должна
существовать в коде вообще: **встроенные провайдеры — это ровно те же модули, просто
лежащие в репозитории.** Если в загрузчике появится ветка «а этот наш» — архитектура
неверна. Проверяется тестом: временный перенос `packages/providers/deepseek/` в
пользовательский каталог не меняет поведения ни в чём.

## Решение

### 1. Модуль провайдера = каталог, а не пакет npm

```
my-cool-image-service/
├─ provider.yaml            обязателен — единственное, что делает каталог модулем
├─ fixtures/
│  ├─ capture-2026-08-27.json     санитизированный CaptureBundle
│  └─ contract.json               ожидания для офлайн-теста
├─ adapter.ts                опционально — только уровень 3 ADR-0002
├─ README.md                 опционально
└─ module.json               опционально — метаданные для шаринга (автор, лицензия, версия)
```

Пути обнаружения, в порядке приоритета (побеждает более специфичный):

1. `--provider-dir <path>` в командной строке;
2. `$OMNIPROXY_PROVIDER_PATH` (разделитель — платформенный);
3. `~/.omniproxy/providers/*/` — каталог по умолчанию, куда кладёт `omniproxy provider init`;
4. `packages/providers/*/` — встроенные, ровно на тех же правах.

Никакой установки, сборки и `npm publish`. Скопировал каталог — провайдер появился.
`omniproxy provider list` показывает источник каждого модуля.

### 2. Граница доверия — прямое следствие запрета кода в YAML (ADR-0002)

| Уровень модуля | Что это | Доверие | Как загружается |
|---|---|---|---|
| Только `provider.yaml` (+ transforms из белого списка) | **данные** | не требуется | загружается сразу, без вопросов |
| `adapter.ts` (уровень 3) | **исполняемый код** | требуется явное согласие | не загружается, пока пользователь не подтвердил |
| `adapter.browser.ts` | код + браузер | требуется явное согласие | то же |

Декларация не может выполнить произвольный код — по построению. Поэтому
**декларативным модулем можно безопасно обменяться** (файл в issue, gist, сообщение в
чате): худшее, что он сделает, — сходит по HTTP на указанный домен с указанными
заголовками. Домены при этом ограничены: движок разрешает исходящие запросы только к
хостам из `channels[].base` и `allowedHosts` декларации; попытка постучаться в другое
место — типизированная ошибка, а не молчаливое исполнение (SSRF-защита §6.9
распространяется и на декларации).

Код-адаптер — другое дело. Правило: при первом обнаружении `adapter.ts` в
пользовательском каталоге CLI показывает путь, хеш файла и требует
`omniproxy provider trust <id>` (либо `--allow-code` для неинтерактивных запусков).
Хеш запоминается; изменился файл — доверие сбрасывается и запрашивается заново.
Исполнение — в `node:worker_threads` с `AdapterCtx` в качестве единственного канала
наружу (`fetch`, `fs`, `process.env` в воркере не проксируются). Это не песочница
военного уровня — воркер не защищает от намеренно вредоносного кода, — но он
защищает от **случайного** вреда и от падения, уносящего gateway. Так и сказать в
документации, без преувеличений.

### 3. Конвейер для пользователя — три команды

```
omniproxy provider init <id>          # интерактивный мастер: имя, домен, модальность
omniproxy capture record <id>         # поднимает Chrome, ждёт логин + один сценарий
omniproxy provider try <id>           # прогон на живом аккаунте с подробным разбором
```

`init` создаёт каталог, спрашивает модальность (текст / картинка / видео / аудио / 3D)
и по ней подставляет каркас — синхронный `flow.send` либо `submit`/`poll`/`artifacts`.
`capture record` (PR-7 фазы 1) снимает трафик, санитизирует, генерирует черновик
`provider.yaml` и фикстуры. `try` исполняет декларацию с трассировкой каждого шага:
какой запрос ушёл, что вернулось, какой JSONPath не нашёлся, чем фактический ответ
отличается от фикстуры. Диагностика — не «ошибка 500», а «`stream.map.text` указывает
на `$.choices[0].delta.content`, но в кадре есть только `$.delta.text` — исправьте так».

`omniproxy provider validate <id>` и контрактный тест на фикстурах доступны
пользователю той же командой, что и разработчику проекта.

### 4. Совместимость — теперь публичное обязательство

Как только модули пишут посторонние, `schemaVersion` перестаёт быть внутренней деталью:

- поддерживаются текущая и предыдущая мажорные версии схемы одновременно;
- `omniproxy provider migrate <id>` переписывает декларацию под новую версию
  автоматически, где это возможно, и оставляет `# TODO(migrate)` там, где нет;
- удаление имени из реестра transforms — ломающее изменение, требует мажора и
  периода депрекации в один релиз;
- при загрузке модуля с неизвестной будущей версией схемы — провайдер помечается
  `unsupported-schema` и **не роняет старт**; всё остальное работает.

### 5. Что запрещено и остаётся запрещённым

Модульность не отменяет §12.9. Механизм даёт пользователю подключить **свой личный
аккаунт** к сервису, которым он и так пользуется. Шаблоны и документация не содержат
и не будут содержать примеров массовой регистрации, подстановки чужих учётных данных
и обхода платных лимитов. Провайдерам, требующим оплаты за генерацию, в мастере
показывается предупреждение о ToS и о риске блокировки аккаунта.

## Влияние на план фаз

Пользовательские модули перестают быть «фазой 7». Правильный порядок:

- **Фаза 1** — конвейер захвата (без изменений), но с самого начала пишется как
  пользовательский инструмент: команды `capture record` / `analyze` работают с
  произвольным `<id>`, а не только со встроенными.
- **Фаза 2** — загрузчик модулей из внешних каталогов и граница доверия попадают в
  ядро сразу, вместе с реестром. Дописывать это потом — переделывать реестр.
- **Фаза 3** — `provider init` / `try` / `validate` / `migrate` и `docs/authoring-a-provider.md`
  на русском и английском. Провайдеры класса B при этом делаются **тем же путём, что
  и пользовательские** — это и есть проверка, что путь рабочий.
- Реестр общедоступных модулей (шаринг деклараций сообществом) — отдельная задача,
  осознанно вне основного плана: он требует модерации и доверия, а декларациями и
  так можно обмениваться файлом.

## Последствия

- Ценность продукта смещается с длины списка провайдеров на качество конвейера —
  что совпадает с метрикой MTTR из §9.
- `docs/adding-a-provider.md` становится документацией **публичного API**, а не
  внутренней инструкцией. Требования к её точности соответственно выше.
- Целевой показатель ADR-0002 приобретает второй смысл: доля декларативных модулей —
  это ещё и доля пользователей, которые смогли подключить свой сервис, не написав кода.
