# ADR-0004 — Масштабная инвариантность: 1 аккаунт ↔ флот, 1 человек ↔ мультиарендность

- Статус: accepted (решение заказчика, 2026-08-27)
- Отменяет: оценку риска R-4 в первоначальной редакции
- Контекст: на вопросы 1 и 2 получены ответы — аккаунтов у пользователя может быть
  сколько угодно (кто-то один, кто-то сто), и мультиарендность нужна полноценная,
  с помощью пользователю, а не с препятствиями.

## Проблема

Соблазн — написать «простой путь» для одиночки и «сложный» для флота, с развилкой
где-нибудь в планировщике. Это всегда заканчивается двумя полупротестированными
режимами: одиночный работает, потому что им пользуются, многопользовательский гниёт.
Или наоборот — одиночка платит сложностью за чужой сценарий и получает требование
поднять Postgres ради одного аккаунта.

## Решение: одна модель, вырождающаяся до тривиального случая

Никаких режимов. Существует **ровно один** код-путь, в котором частные случаи —
это значения, а не ветки:

| Понятие | Одиночка | Команда / сервис |
|---|---|---|
| Tenant | один неявный `default` | много, с ключами и скоупами |
| AccountPool | один пул, один аккаунт | много пулов, десятки аккаунтов |
| Квоты тенанта | не заданы = без ограничений | заданы, честное разделение |
| Аутентификация клиента | выключена на loopback | обязательна, fail-closed |
| Repository | драйвер `file` | `sqlite` или `postgres` |

Развилка «если пользователь один» в коде запрещена и проверяется тем же линт-правилом,
что и `if (provider === ...)`. Одиночный сценарий — это конфиг по умолчанию, а не
отдельная реализация.

## 1. Аккаунты: пул как первичное понятие

```
Provider ──< AccountPool ──< Account ──< Lease
                  │
                  └──> назначен одному или нескольким Tenant (shared | dedicated)
```

- **Account** — учётные данные + состояние: `active | cooldown | degraded | quarantined |
  needs-reauth`, привязанный прокси, привязанный отпечаток, счётчик квоты.
- **Lease** — аренда аккаунта под конкретный запрос, с TTL и владельцем.
  Аренда живёт в Repository с оптимистичной блокировкой, поэтому несколько воркеров
  и несколько процессов не могут одновременно взять один аккаунт. При N=1 механизм
  тот же, просто очередь на аренду короткая. Это не оверинжиниринг: без аренды
  двухпроцессный запуск (gateway + worker) сжигает аккаунт параллельными запросами.
- **Привязки, которые нельзя нарушать:** аккаунт ↔ прокси (смена выходного IP у
  залогиненной сессии = бан), аккаунт ↔ отпечаток браузера, клиентская сессия ↔ аккаунт
  (пока аккаунт жив). При вынужденной смене аккаунта переносится recovery-история —
  механизм уже есть в `server.js:1531-1616`.

## 2. Квоты: измеряем, а не верим

У web-сервисов лимиты не документированы и меняются. Поэтому:

- **QuotaLedger** на аккаунт: расход в единицах провайдера (`message | generation |
  credit`), окно сброса, время следующего сброса.
- Заявленный в декларации `quota.perDay` — не истина, а начальная гипотеза.
  Фактический лимит **выучивается**: получили 429 или «лимит исчерпан» на N-й
  генерации — записали N как наблюдаемый потолок, сдвинули оценку. Через несколько
  циклов оценка становится точнее декларации.
- **Предиктивный cooldown:** аккаунт выводится из ротации при подходе к выученному
  потолку, а не после отказа. Отказ стоит дороже: он часто сопровождается штрафом
  и подозрением на стороне провайдера.
- **Резерв** (`quotaReservePct`): часть квоты не отдаётся фоновым задачам — чтобы
  канарейка и интерактивный запрос человека не остались без ресурса, потому что
  ночной батч всё выел.

## 3. Планировщик: две шкалы одновременно

Целевая функция — не «деньги» и не «скорость», а **сохранение дефицитной квоты при
соблюдении обещанной надёжности**. Порядок отбора кандидатов:

1. отсечь несовместимых по capability (жёстко, `strictCapabilityMatch`);
2. отсечь мёртвых: карантин, красная канарейка старше `maxCanaryAgeMs`, `needs-reauth`;
3. предпочесть sticky-аккаунт этой сессии, если он здоров и не на пределе квоты;
4. дальше — по политике: `most-quota-left` (по умолчанию) | `fastest` | `least-loaded` |
   `best-quality` | `manual` с весами.

При одном аккаунте шаги 3–4 схлопываются, и работает межпровайдерный fallback.
При флоте — те же шаги дают полноценную балансировку. Ни строчки различий.

## 4. Мультиарендность: разрешать и помогать

- **Tenant** с ключами (скоупы `text:*`, `image:*`, `video:generate`, `admin`),
  собственными квотами (запросов в минуту/день, дисковый бюджет артефактов) и
  назначенными пулами аккаунтов.
- **Честное разделение:** взвешенная справедливая очередь поверх дефицитной квоты
  аккаунтов. Один тенант не может выесть флот, даже если шлёт в сто потоков;
  его запросы просто ждут в своей очереди. При одном тенанте очередь всегда пуста —
  накладные расходы нулевые.
- **Изоляция:** артефакты, сессии, job'ы и логи разделены по `tenantId` на уровне
  Repository, а не на уровне «мы стараемся не перепутать». Тест на утечку
  межтенантных данных обязателен.
- **Помогать, а не мешать:** `omniproxy tenant add`, выдача ключа, готовый пример
  nginx/Caddy с TLS, раздел «как поднять это для команды» в документации, в
  admin-UI — страница тенантов с их расходом квоты. Раз пользователь хочет
  раздать доступ друзьям или команде — это поддерживаемый сценарий, а не то,
  что приходится обходить.
- **Единственная жёсткость:** при `bind` не на loopback аутентификация клиента
  обязательна и включается сама (fail-closed). Открыть шлюз в мир без ключа можно
  только явным `--allow-anonymous-public`, с честным предупреждением в логе:
  наружу торчит доступ к вашим личным аккаунтам.

## Последствия

- Repository и Job-модель обязаны поддерживать конкурентный доступ из нескольких
  процессов с самого начала — это влияет на фазу 2, дописать потом дороже.
- Драйвер `file` тоже обязан быть корректным при двух процессах (файловые блокировки,
  атомарная запись через temp+rename). Иначе «однокомандный запуск» окажется
  единственным, где всё ломается.
- Риск R-4 закрыт: планировщик получает осмысленную работу в обоих сценариях.
  Взамен появляется R-12 (поверхность мультиарендности) — см. реестр рисков.
