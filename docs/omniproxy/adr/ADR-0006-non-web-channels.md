# ADR-0006 — Каналы, не являющиеся веб-интерфейсом: `app-backend` и `local-process`

- Статус: proposed
- Дата: 2026-08-27
- Контекст: заказчик прислал рабочий прокси к внутреннему бэкенду десктопного
  приложения AutoClaw (z.ai) и предложил расширить проект так, чтобы пользователь мог
  подключать **чужие прокси**, а не только веб-интерфейсы.

## Что показал присланный код

`autoclaw-proxy` — 200 строк, которые говорят с
`autoglm-api.autoglm.ai/autoclaw-proxy/proxy/autoclaw/chat/completions`. Разбор:

| Элемент | Что это на самом деле |
|---|---|
| `Authorization: Bearer autoclaw-internal-proxy` | константа, вшитая в десктопное приложение, — не секрет пользователя |
| `X-Authorization: <JWT>` | персональный токен, читается из `~/.openclaw-autoclaw/request-headers.json`, обновляется самим приложением |
| `X-Client-Type: pc`, `X-Product`, `X-Harness-Type`, `X-Tm: win`, `X-Version: 1.17.8`, `X-Channel` | отпечаток клиента: бэкенд ждёт, что с ним говорит именно десктоп |
| `MODEL_MAP` | клиентское имя → внутренний id (`glm-5.3` → `zaicoding_glm-5.3`) |
| SSE от бэкенда | уже OpenAI-совместимый: `data: {...}`, финал `data: [DONE]` |
| комментарий про WAF | Aliyun edge пропускает **только TLS-отпечаток Node/undici**, httpx получает 405 |

Три вывода, каждый из которых меняет наш дизайн.

### Вывод 1. Это новый вид канала, а не разновидность `web-http`

Авторизация приходит не из браузерной сессии, а из **локального файла состояния
десктопного приложения**. Эндпоинт — не тот, в который ходит браузер, а тот, в который
ходит установленная программа. Это отдельный тип: `app-backend`.

Класс не экзотический. Токен в локальном конфиге — типовое устройство десктопных
AI-клиентов, и один раз реализованный харвестер «прочитать JSON-файл, взять значение
по пути» откроет целую категорию провайдеров, к которым через браузер не подступиться.

### Вывод 2. Отпечаток — не всегда «притворись Chrome»

ADR-0001 вводил слой имперсонации ради Cloudflare, то есть чтобы выглядеть браузером.
Здесь требование обратное: выглядеть **Node/undici**, потому что именно так ходит
десктопное приложение, и WAF настроен на него. Значит, профиль отпечатка — это не
шкала «более или менее браузерный», а именованный набор, выбираемый по свидетельству
из захвата. В реестр профилей добавляется `node-undici` (и он же — самый дешёвый,
поскольку это наш собственный дефолт).

### Вывод 3. Весь этот прокси выражается декларацией

Проверка ADR-0002 на живом примере. В терминах `provider.yaml`:
`base` + `channels[].fingerprint.profile: node-undici` + статические заголовки +
`auth.kind: local-file` с путём и JSONPath + `models[].native` вместо `MODEL_MAP` +
`stream.format: sse` с OpenAI-мэппингом. **Ни одной строки кода.**

Это сильный аргумент за декларативный подход: то, что автор написал как программу,
у нас — конфигурация, которую можно править на ходу и чинить без пересборки.

## Решение

### 1. Добавляется тип канала `app-backend`

```yaml
channels:
  - id: desktop
    kind: app-backend          # web-http | web-browser | gateway-protocol | app-backend | local-process
    base: https://autoglm-api.autoglm.ai
    fingerprint:
      profile: node-undici     # ждут десктопный клиент, а не браузер
```

### 2. Добавляется источник авторизации `local-file`

```yaml
auth:
  kind: local-file
  harvest:
    file:
      # по платформам, потому что ADR-0005
      win32:  "%USERPROFILE%\\.openclaw-autoclaw\\request-headers.json"
      linux:  "$HOME/.openclaw-autoclaw/request-headers.json"
      darwin: "$HOME/.openclaw-autoclaw/request-headers.json"
    extract:
      token: $.headers.X-Authorization
    watch: true                # файл переписывается приложением — перечитывать
```

`watch: true` — важная деталь: приложение обновляет JWT само, и наш планировщик
refresh'а здесь не нужен, нужен только следящий за файлом. Это дешевле и надёжнее,
чем собственный refresh, и это ровно тот случай, когда правильное решение —
не делать работу, которую уже делает кто-то другой.

Файл читается только на чтение, значение никогда не логируется и попадает под те же
правила, что cookie: шифрование в credential-store, `sha256[:8]` в логах.

### 3. Добавляется тип канала `local-process` — «принеси свой прокси»

Для случаев, когда чужой прокси переписывать не нужно или нельзя (тяжёлая логика,
Python-зависимости, чужая лицензия), OmniProxy умеет **запускать его сам** и говорить
с ним как с обычным upstream:

```yaml
channels:
  - id: managed
    kind: local-process
    process:
      command: node
      args: [./vendor/autoclaw-proxy.js]
      env: { PORT: "{{channel.port}}" }
      cwd: .
      port: auto               # выделяем свободный, подставляем в env
      readyWhen:
        request: { method: GET, path: /v1/models }
        timeoutMs: 15000
      restart: { maxAttempts: 5, backoffMs: 1000, maxBackoffMs: 30000 }
      stopSignal: SIGTERM      # на Windows — завершение дерева процессов
    speaks: openai             # диалект, на котором отвечает процесс
```

Что даёт пользователю по сравнению с «запустить прокси руками»: единая точка входа,
учёт квот и аккаунтов, цепочки fallback на других провайдеров, канарейки, общие логи
с traceId, участие в виртуальных алиасах вроде `omni/best-text`. Пользователь только
описывает конфигурацию — запуск, перезапуск, здоровье и остановка на нас.

**Граница доверия.** Запуск произвольного исполняемого файла — это исполнение кода,
ровно как `adapter.ts` из ADR-0003. Поэтому тот же гейт: канал `local-process` не
стартует, пока пользователь не подтвердил `omniproxy provider trust <id>`; хеш команды
и аргументов запоминается, изменение сбрасывает доверие. Декларация с `local-process`
не считается «данными» и не может быть безопасно расшарена как обычная.

**Кроссплатформенность (ADR-0005).** Завершение дочернего процесса — разное на
платформах: группа процессов и `SIGTERM` на POSIX, `taskkill /T /F` по дереву на
Windows. Порт выделяется динамически. Никаких предположений про shell — запуск
только через `spawn` без `shell: true`, иначе аргументы с пробелами станут дырой.

### 4. Что предпочитать

| Ситуация | Канал |
|---|---|
| Эндпоинт и заголовки известны | `app-backend` декларацией — дешевле, быстрее, чинится правкой YAML |
| Логика прокси сложная, чужая или на другом языке | `local-process` |
| Нужен и тот и другой | оба, как ступени деградации в одном провайдере |

Порядок в `channels` — это порядок деградации (§6.3), так что «декларация, а если она
сломалась — управляемый процесс» описывается штатно, без новых понятий.

## Что мы НЕ делаем

- **Не встраиваем чужой код в репозиторий.** `local-process` запускает то, что лежит
  у пользователя, а не то, что мы вендорим. Чужая лицензия — не наша забота ровно до
  тех пор, пока мы её не копируем.
- **Не объявляем AutoClaw поддерживаемым.** Присланный исходник — отличное свидетельство,
  но это не захват: я не могу проверить ни что эндпоинт жив, ни что заголовки полны,
  ни что файл с JWT существует у конкретного пользователя. Дословно по правилу §12.1:
  черновик декларации по исходнику писать можно, статус — `unverified`, зелёным он
  станет после одного живого прогона. Досье: `docs/providers/autoclaw.md`.
- **Не делаем «сквозной passthrough».** Соблазн: бэкенд уже говорит OpenAI-SSE, можно
  просто переливать байты. Нельзя — тогда мимо пройдут маршрутизация, квоты, fallback,
  метрики и tool-протокол. Поток так же разбирается в UMS-события; для OpenAI-совместимых
  источников это дешёвый мэппинг, который декларация и так описывает.

## Замечания по присланному коду (для нашей реализации)

Разбирал построчно; четыре вещи, которые в нашей версии должны быть иначе:

1. **`AbortController` создаётся, но его сигнал не передаётся в `fetch`.** `res.on('close')`
   вызывает `ctrl.abort()`, и это не делает ничего: запрос к бэкенду продолжает жить
   после ухода клиента. У нас отмена идёт через `AdapterCtx.signal` и проверяется тестом.
2. **Ретрай только на стриминговом пути.** `handleNonStream` падает с первой сетевой
   ошибки, `handleStream` пробует дважды. Политика ретраев должна быть одна и жить в
   транспорте, а не в обработчике.
3. **Неизвестная модель молча становится `zai_glm-5.3-flash`.** Тихая подмена модели —
   худший вид неожиданности: клиент думает, что получил ответ запрошенной модели.
   У нас неизвестный алиас — типизированная ошибка с перечнем доступных.
4. **`fin` всегда пустая строка**, а `buf = lines.pop()` может вернуть `undefined` —
   мелочи, но показательные: этот класс ошибок ловится `strict` TypeScript на компиляции.

Ничего из этого не умаляет ценности исходника: он даёт то, чего я не могу получить
сам, — реальные эндпоинт, заголовки и карту моделей.

## Последствия

- `Channel.kind` расширяется до пяти значений; `ChannelDescriptor` в `03-interfaces.ts`
  и схема `provider.yaml` обновляются.
- Появляется подсистема супервизии процессов (в `packages/transport`, за интерфейсом
  `LocalProcessChannel`) — реализация в фазе 2 вместе с транспортом.
- Харвестер `local-file` — самая дешёвая часть `packages/auth` и, вероятно, первая.
- Матрица провайдеров получает новый столбец: класс H — «бэкенды десктопных приложений».
  Ожидание по сложности: между B и C. Anti-bot обычно нет, но есть версионный отпечаток
  клиента, который протухает при обновлении приложения.

## Границы: мы делаем механизм, а не интеграции (уточнение заказчика, 2026-08-27)

Для сторонних прокси OmniProxy предоставляет **только основу — исполнение**.
Всё остальное настраивает пользователь. Явно:

**Что делаем мы**
- Супервизор процесса: запуск, ожидание готовности, перезапуск с backoff, остановка,
  корректное завершение дерева процессов на обеих платформах.
- Выделение порта, проброс переменных окружения, сбор stdout/stderr в наши логи
  с общим `traceId`.
- Маршрутизация к поднятому процессу как к обычному upstream: алиасы, квоты,
  цепочки fallback, канарейки, метрики.
- Гейт доверия и внятные ошибки: не запустился — сказать, что именно упало и где
  лежит лог.
- Схему конфигурации и её валидацию с понятными сообщениями.

**Что делает пользователь**
- Приносит сам прокси: скачивает, кладёт куда хочет, отвечает за его лицензию,
  зависимости и работоспособность.
- Пишет конфигурацию: команда, аргументы, окружение, диалект, проверка готовности.
- Держит его в актуальном состоянии, когда сторонний сервис меняется.

**Чего мы не делаем никогда**
- Не вендорим чужой код в репозиторий.
- Не ведём каталог сторонних прокси и не обещаем, что какой-то из них работает.
- Не чиним чужой прокси и не подстраиваемся под его особенности в ядре: если он
  говорит на своём диалекте — это его дело, наше дело — `speaks: openai` и
  задокументированный контракт.

Причина ровно та же, по которой пользовательские модули провайдеров — данные, а не
наш код (ADR-0003): ценность в конвейере и в исполнении, а не в длине списка
поддерживаемого. Список гниёт, механизм — нет.

Практическое следствие для `docs/providers/autoclaw.md`: это **разобранный пример**,
показывающий, как выглядит конфигурация такого канала, а не провайдер, который мы
берёмся поддерживать. Если он у кого-то заработает — он живёт в
`~/.omniproxy/providers/autoclaw/` как модуль этого пользователя.
